# 架构与设计取舍

## 一条执行链

浏览器提交问题、服务、场景和窗口 → `RunController` 验证输入 → `RunService` 保存 QUEUED 记录并调度 → 依次调用三个只读工具 → `DemoReasoner` 根据本次证据生成结构化结论 → `EvidenceValidator` 检查引用 → 保存终态。

`RunEventController` 每 200ms 读取持久化快照，将尚未发送的事件通过 SSE 推送。`app.js` 使用事件序号去重，结果通过 `textContent` 渲染；引用只跳转到同一次执行的证据。

这是阶段 A 的固定执行路径。阶段 B 将使用 Spring AI 替换固定工具选择与结论生成，复用工具契约、证据验证、执行预算和存储层。当前不把确定性流程描述成模型自主决策。

## 分包与阅读顺序

| 包 / 文件 | 责任 | 建议掌握的问题 |
|---|---|---|
| `domain/TriageModel` | 不可变执行、事件、证据和结论契约 | 为什么事件和证据分开？ |
| `tools/ToolContext` | 固定服务、场景、时间窗 | 用户切换场景为什么不影响已有执行？ |
| `tools/*Tool` | 三个只读适配器 | 输入输出怎样约束？ |
| `execution/RunService` | 调度、预算、失败、恢复 | 超时任务为何不能提交迟到结果？ |
| `execution/EvidenceValidator` | 引用归属校验 | ID 存在是否等于结论正确？ |
| `store/RunRepository` | JDBC + JSON 快照 | 如何保证状态与事件同批保存？ |
| `api/RunEventController` | 持久化事件重放 | 执行先结束，浏览器后连接会怎样？ |
| `static/app.js` | 展示与交互 | 切换历史时怎样防止旧请求覆盖新页面？ |

## 状态与边界

状态流：`QUEUED → RUNNING → SUCCEEDED / INSUFFICIENT_EVIDENCE / FAILED`。队列满或排队预算耗尽也可以从 QUEUED 进入 FAILED。SUCCEEDED 表示流程得到了有证据的判断，并不表示模型正确率或真正根因已经确认。

每个执行只有一个协调任务写状态。工具任务只返回数据，不持有数据库写入入口；工具超时后 `Future.cancel(true)` 请求中断，协调器写失败，迟到返回值不会再次写结果。不响应中断的工具仍可能占用线程，因此运行和工具分别使用 4 线程 + 16 等待位的有界池。新执行排队失败返回 HTTP 429。当前工具只有本地内存 / 随仓库文件查询，不做外部 I/O。

总时长用单调时钟计算，在出队、每次调用和结论前后检查；单次等待取工具预算与剩余总预算的较小值。数据库等待与 JVM 调度不是硬实时约束。默认 3 次调用、2s 单工具、10s 总预算。SSE 最多 64 个连接，连接在完成、异常、25s 超时后释放；数据仍在数据库。

启动时把未结束记录标为 `FAILED / SERVER_RESTARTED`，保留已采集事件和证据，不自动重跑。此设计仅支持单实例；多实例启动恢复需要租约 / 实例归属，本轮不实现。

## 取舍 1：先固定规则，再接真实模型

先证明产品链路、证据合同和失败边界，再让模型决定工具调用。好处是没有密钥也能演示和回归；代价是阶段 A 不具备开放问题理解或自主工具选择。网页和 README 显式标明 DEMO，不能把演示成功率当作模型效果。

## 取舍 2：三个 Markdown 文档使用关键词检索

当前语料只有三个短文档。固定 ID 和透明关键词足以检查引用，避免引入 embedding、向量索引和额外费用。代价是同义改写可能漏召回；`查看健康状态` 在超时场景下能读取指标，但没有命中超时规则时会返回证据不足。阶段 B 再根据实际召回问题决定是否升级检索。

## 取舍 3：本机 H2 + PostgreSQL 共用 JDBC 存储

H2 文件库减少初次体验门槛，PostgreSQL 提供更接近后端项目的持久化路径。两个模式共用 Flyway SQL 和仓库实现，都运行真实 HTTP 测试。没有提前引入 ORM、向量扩展或多套存储。代价是 H2 不能替代 PostgreSQL 兼容性验证，CI 因此保留独立数据库作业。

## 取舍 4：一行 JSON 快照 + SSE 重放

一次数据库 UPDATE 同时保存执行状态、事件和证据，避免事件已发但历史缺失。每次执行最多 10 次工具调用，快照规模有限；列表只返回摘要。SSE 从持久化记录读取，因此不会丢失“订阅之前已结束”的事件。代价是重复写 JSON、200ms 轮询和列表先读取完整快照；只适合当前小规模单体。未来数据量增长再拆事件表或引入订阅通知。

## 证据校验能保证什么

每条观察 / 原因引用非空，且所有 ID 来自本次返回；重复 ID 拒绝。它保证可追溯性，不保证自然语言结论在语义上被引用支持。当前固定模板人工核对；真实模型接入后还需要案例评测与人工语义审核。指标中缺少数据库、网络、库存资源观测，不能确认超时最终根因。
