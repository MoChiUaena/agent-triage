# PR 协同检查

在“研发协作”填写 PR 编号，选择可选的 Issue 编号或已有报告，点击“生成执行计划”。计划显示固定的 base/head 和七个任务，确认后异步执行。页面显示每步依赖、状态、来源及综合报告，切换仓库后也可从最近记录重新打开。

任务依次读取仓库、审查 PR、分诊 Issue、排查 CI、核对证据、进行一次有界补查并汇总。需要前置任务成功的步骤会在失败后跳过；独立的 Issue 分诊，以及核验和汇总仍会继续。没有选择 Issue 时，只取 PR 正文首个同仓库明确引用，没有引用则跳过。

新 Issue 分诊只使用本机规则。可以选择同仓库已有的模型建议报告，保留其生成时间与版本；工作流不会重新发送模型数据。CI 可自动读取所选 head 的 Actions，也可纳入已有报告。已保存的 GitHub 日志须核对相同提交、当前尝试和失败作业；其他提交、旧尝试、未验证的粘贴日志不会直接进入适用来源。

发现版本或状态不一致时最多补查一次。新 PR 版本需要重新生成计划，Issue 更新需要新的分诊预览；不会自动改分析目标或重发模型上下文。补查失败时仍保留任务历史，但已知不适用的来源和行动项会从综合报告排除。当前检查覆盖 PR SHA、Issue 元数据及 CI 提交、来源、尝试和作业，不核对完整 Issue 正文、评论或业务根因。

自动 CI 排查只读取同一 head 的前五个 Actions 运行，分析一个失败运行的首个失败作业，作业列表最多五十个；合并提交和第三方 CI 日志不在此范围。没有读取到运行、仍在执行、权限失败和未知检查状态分别保留缺口，不计作通过。

综合报告展示需要重建计划、材料不完整、有待核对提醒或继续人工核查，并链接到适用的 PR、Issue 和 CI 报告。任务结束表示编排结束，仍需核对完整代码、测试覆盖与合入条件。当前支持固定 PR 模板，尚不能编辑任意任务图或自动修复。

最多两个并发工作流，每次最多三分钟，可在页面取消。每个任务完成后保存结果；重启将未结束工作流标为中断，不自动重跑。计划保存在内存中，五分钟内有效，最多保留 40 份。执行和证据保存在本机数据库，最近展示 20 次；移除仓库登记会一并清理。

| 方法 | 路由 | 用途 |
|---|---|---|
| POST | `/api/development/repositories/{id}/workflows/plans` | 生成计划：`prNumber` 必填，`issueNumber`、`issueReportId`、`ciReportId` 可选 |
| POST | `/api/development/repositories/{id}/workflows` | 提交 `planId`，返回 202 与工作流 ID |
| GET | `/api/development/repositories/{id}/workflows` | 最近执行 |
| GET | `/api/development/workflows/{workflowId}` | 任务状态和已保存结果 |
| POST | `/api/development/workflows/{workflowId}/cancel` | 取消执行 |

写入本机状态需要 `X-Triage-Development: 1`，接口沿用本机同源保护。所有外部 GitHub 请求只读，完整日志不写入工作流，凭据不进入报告。
