# 实施计划

目标：完成能演示、能测试、能解释设计取舍的 Java 故障排查项目。用户首轮投入预算约 30–40 小时；由 AI 负责实现、验证和提交，用户重点参与运行体验、场景判断和关键设计理解。

## 范围

一个单体、一个 Agent、三个只读工具、一个下游超时故障和正常对照。所有演示数据明确标记 synthetic。首版不执行 Shell / SQL 修复，不做多 Agent、任意上传、多租户或向量数据库平台。

## A — 可运行的确定性演示（本轮）

- [ ] Java 21、Maven Wrapper、固定依赖和可复制的启动命令。
- [ ] 固定的正常 / 下游超时模拟适配器；每次运行冻结场景。
- [ ] 文档检索、指标读取、错误日志查询三个有界工具。
- [ ] 提问 → 事件 → 证据 → 结论 → 持久化历史。
- [ ] 简单网页、SSE 进度、历史浏览、场景选择。
- [ ] 调用次数、工具超时、总时长、并发和队列上限。
- [ ] 离线测试、端到端验证、CI、公开仓库。

验收：无模型密钥启动；正常和故障结果可复现；每条结论引用均属于本次证据；服务重启后记录仍在；失败与证据不足是不同状态。

## B — 真实单 Agent（下一轮）

- [ ] Spring AI ChatClient + 三个工具回调，模型可选择工具和停止。
- [ ] 一个模型服务，环境变量配置，不记录原始敏感请求或凭据。
- [ ] 复用阶段 A 的证据验证、时间预算和状态机。
- [ ] 处理工具异常、模型循环、无效引用和结构化输出失败。
- [ ] 分别说明确定性模式与真实模型模式、费用和人工核查步骤。

验收：一次真实模型调用有可核查证据；无效输出不得伪装成功；普通 CI 不调用付费 API。

## C — 小规模评测

- [ ] 20 个人工审核案例，10 调试 / 10 保留；固定数据集版本。
- [ ] 正常、超时、无关问题、证据不足、工具失败。
- [ ] 仅检索问答与工具 Agent 对比，保存原始结果和失败案例。
- [ ] 记录模型、参数、样本数、工具选择、引用、状态、耗时；usage 缺失时留空。

验收：报告只能引用实际运行记录；不得将调过参数的保留集继续称为独立效果证明。

## D — v0.1 交付

- [ ] README 截图 / 短演示、架构、三个设计取舍、一个真实失败案例。
- [ ] 演示脚本、已知限制、许可证、贡献说明。
- [ ] 真实模型验证与评测完成后创建 v0.1 发布内容。

## 提交原则

每个提交对应一个可审查的功能、修复、测试或文档增量；尽量多积累真实有效的改动，不制造空提交、不补造日期、不夸大完成情况。阶段 A 完成不等于 v0.1 全部完成。

## 版本依据（2026-09-27）

- [Spring AI v1.1.8 官方入门文档](https://github.com/spring-projects/spring-ai/blob/v1.1.8/spring-ai-docs/src/main/antora/modules/ROOT/pages/getting-started.adoc) 明确兼容 Spring Boot 3.4.x / 3.5.x。
- Maven Central 已提供 Spring Boot 3.5.16、Spring AI 1.1.8。选择该兼容稳定版本线；不跟随 milestone。
- JDK 21 在本机已存在；仅设置进程级 JAVA_HOME，保留全局 Java 配置。

## 用户每阶段需要掌握

A：三个工具的数据边界、执行状态和 SSE 如何重放。B：模型如何决定工具调用、为什么必须验证引用。C：如何区分演示结果与模型效果证据。D：如何用五分钟讲清问题、架构、限制和失败案例。
