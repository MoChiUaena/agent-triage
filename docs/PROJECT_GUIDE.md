# 项目导览

Agent Triage 用于排查 Java 服务的慢请求。选择服务和时间窗口、输入问题后，它读取指标、错误日志和排障文档，给出带引用的判断与下一步检查建议。当前覆盖 HTTP 下游超时、数据库连接池耗尽和 SQL 执行阶段失败。

## 一次排查会得到什么

| 视图 | 内容 | 用法 |
|---|---|---|
| 概览 | 窗口指标、初步判断、检查建议和不确定性 | 先看本窗口实际发生了什么 |
| 证据 | 指标原值、最多 3 条错误事件、匹配的规则 | 点击结论中的引用，核对判断依据 |
| 执行记录 | 工具与模型调用顺序、反馈、失败或取消 | 确认缺少证据，还是调用本身出了问题 |
| 代码引用 | 接口入口、业务错误行、静态调用关系与构建摘要 | 核查运行服务和当前源码是否对应 |

“已完成”表示当前判断通过了证据校验，不表示故障已经修复。“证据不足”表示观测不能支持完整判断；失败和取消则表示本次执行没有生成最终结论。新记录保留提交时的服务名称、模型来源和时间窗口，旧历史仍可读取；重新打开不会再次调用模型。

## 从两个例子理解结果

### HTTP 下游超时

订单样例通过 HTTP 调用库存样例。故障场景让库存接口延迟 600ms，而订单客户端的请求总时限为 300ms，实际订单请求因此返回超时。Agent 查询订单侧的窗口请求数、调用耗时、超时次数和带 traceId 的错误事件。

有请求、有下游超时率、存在对应错误日志，再加上匹配的排障规则，才能支持“本窗口观察到下游调用超时”的判断。两个 p95 接近不能证明全部订单耗时来自库存，也不能确认库存内部根因。运行方法见[本地请求链路](LIVE_LAB.md)。

### 数据库连接池耗尽

数据库样例使用真实 HikariCP 和内存 H2。实验操作借出全部池连接，后续查询在获取连接阶段超时；窗口观测同时记录池占用、等待线程和对应阶段的错误。

只有获取连接超时、池满与等待重叠的采样、对应日志和规则同时成立，才支持连接池耗尽判断。已经拿到连接、随后因 SQL 行锁等待而失败的请求，会记为查询阶段错误，不能替代获取连接超时证据。释放故障连接后，再用新的正常窗口检查请求恢复。运行方法见[数据库连接池排查](DATABASE_POOL.md)。

## 运行模式和数据来源

这两组设置分别决定如何判断、从哪里取数：

| 设置 | 取值 | 行为 |
|---|---|---|
| 判断模式 | `DEMO` | 依次执行三个只读工具，由固定规则生成判断 |
| 判断模式 | `MODEL` | 模型选择工具、判断类型、证据和候选检查项，应用校验后生成措辞 |
| 数据来源 | `SYNTHETIC` | 使用固定的订单演示指标与日志，无需启动样例服务 |
| 数据来源 | `LIVE` | 从服务器登记的接口读取实际请求观测 |

`DEMO + LIVE` 已经在使用真实请求数据。`MODEL + SYNTHETIC` 会调用模型，但现场观测仍是固定演示数据。模型模式是否启用，可在设置页选择；服务列表和观测协议从启动配置读取。

首次体验可先按 README 启动订单与库存样例，用 `DEMO + LIVE` 生成请求并核对证据；随后再配置模型，比较同一类观测下的工具选择和检查建议。模型连接测试与模型排查都可能由服务方计费。

## 模型承担的工作

模型最终只提交 `assessment`、`evidenceIds`、`nextChecks`。应用负责检查这些选择是否符合实际观测，再生成页面中的关键结论和数值。模型不能更改服务地址、窗口或执行限额，也没有 SQL、Shell、故障切换和修复工具。

服务参考规则、无请求门槛、一次有界反馈，以及检查项排序由应用提供。因此，结果取决于模型选择和这些约束共同作用，不能把效果全部归为模型独立诊断能力。具体格式见[模型判断契约](MODEL_OUTPUT.md)。

## 看代码与验证

排查的协调、工具和模型执行器各有 4 个工作线程及 16 个排队位置。取消会移除尚未启动的任务，并请求中断已经运行的任务；如果第三方代码忽略中断，它仍可能占用工作线程，迟到结果不会写入已取消记录。页面显示取消成功并不证明外部模型停止计费。服务关闭会释放排队任务的登记，未完成历史在重启时按原有恢复规则处理。

[资源留存验收](validation/2026-10-01-runtime-resources.md)记录五分钟反复取消、异步完成、连接归还、采样关闭和 SSE 回放的检查。运行中的固定工作线程可以保持空闲；历史记录和有界观测样本也会按设计保留。这些结果尚不能证明数天运行、原生内存或任意数据库驱动没有留存问题。

阅读[架构说明](ARCHITECTURE.md)可了解提交、工具调用、判断校验、存储和取消之间的关系。接口和权限见 [API](API.md)，新增服务所需的观测契约见[接入说明](SERVICE_INTEGRATION.md)。

[测试说明](VALIDATION.md)区分单元／HTTP 检查、本地模型协议模拟器和真实模型小样本。数据库与取消场景已经用真实请求及本地协议模拟器验证；已有百炼真实模型报告来自订单／库存场景，不能据此宣称所有场景和供应商都已验证。

当前 main 包含本机源码接入、按接口排查、错误位置、构建摘要核对、可选 JPA 观测与跨线程包装。[v0.10.0 演示包](releases/v0.10.0.md)用于体验订单、数据库、Starter 和工单样例；新 SDK 的可选能力见包内 `OBSERVATIONS.md`，JPA 接入需按[公开 Petclinic 验收](PETCLINIC.md)单独构建。上表为源码各模块的默认端口，包内端口由统一启动脚本分配。项目源码页的“检查接入”会提示观测、流量、源码绑定、入口与版本方面的缺口，具体设置见[源码接入](SOURCE_INTEGRATION.md)。应用目前面向本机单实例，没有多用户登录或跨实例任务协调，也不会自动解析任意 Actuator 或日志格式。
