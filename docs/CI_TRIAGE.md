# CI 失败日志排查

在“研发协作”选择已登记仓库，点击失败工作流旁的“排查 CI”。页面读取该运行尝试的作业，选择一个已结束的失败作业，再点“读取日志并分析”。报告保留仓库、提交 SHA、运行尝试、作业和原日志行号，之后可以从“CI 排障报告”重新打开。

当前分析在本机执行，不调用模型。它识别依赖解析、编译、测试、脚本、权限、连接和超时等失败阶段，整理错误附近的片段、日志提到的文件位置和下一步核查项。能识别阶段不等于确定完整根因；没有匹配的错误证据时显示“证据不足”。文件位置来自日志，尚未核对相应源码。

GitHub 日志下载通常需要 Actions 只读权限。当前访问被拒绝时，可在弹窗展开“粘贴失败日志”，粘贴错误和上下文后分析。报告会标明粘贴来源以及“与作业的对应关系未验证”，不会把粘贴内容当成 GitHub 已核对的事实。GitHub 凭据仍由 `TRIAGE_GITHUB_TOKEN` 提供，见[仓库接入说明](GITHUB_REPOSITORIES.md)；不要把 Token 写进仓库或聊天。

## 证据与范围

- 使用固定的运行尝试和作业 ID；提交 SHA、运行或作业不一致时拒绝生成报告。
- 每次查看最多读取 50 个作业，超出时显示范围提示。只分析已结束的失败作业。
- GitHub 响应最多 1 MiB，每次请求的八秒期限覆盖正文。日志下载仅接受受信的 GitHub Actions 存储地址，下载请求不携带 API Token。
- 有可匹配的时间戳时，只扫描首个失败步骤的时间段；无法匹配时说明扫描范围。相邻步骤的时间边界重叠时，不用共享区段判断原因。报告最多保留六个错误块，并保留原日志文件的行号。
- 粘贴日志最多 200,000 字符。常见 Token、凭据赋值、JSON 凭据和私钥块先脱敏，再生成证据；完整原日志不入库，脱敏处理不能替代检查不常见的敏感内容格式。
- 报告保存于本机数据库，页面显示最近 20 份。确认移除仓库登记时，该仓库的本机 CI 报告一起删除。

所有 GitHub 操作均为读取，日志中的文本不会作为指令执行，也不会自动修改代码、重跑工作流或合并 PR。

API：

| 方法 | 路由 | 用途 |
|---|---|---|
| GET | `/api/development/repositories/{id}/ci/runs/{runId}` | 读取运行尝试和作业 |
| POST | `/api/development/repositories/{id}/ci/reports` | 读取或分析日志并保存报告 |
| GET | `/api/development/repositories/{id}/ci/reports` | 最近 20 份报告 |
| GET | `/api/development/ci/reports/{reportId}` | 查看冻结的报告 |

生成报告需要 `X-Triage-Development: 1`。正文包含 `runId`、`attempt`、`jobId`、`headSha`；可选 `logText` 表示本机粘贴日志。
