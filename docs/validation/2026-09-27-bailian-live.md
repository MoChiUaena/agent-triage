# 百炼 LIVE 链路检查（2026-09-27）

本次使用阿里云百炼 `qwen3.7-flash-2026-07-15`，连接本地独立的订单和库存服务。每组观测由真实 HTTP 请求产生；订单服务使用 300ms 请求总时限。模型配置为温度 0、最多 4 轮、最多 1600 输出 token；首次等待上限 20 秒，随后调到 45 秒。API Key 未写入报告。

| 场景 | 样例请求 | 最终状态 | 工具 / 模型轮次 | 服务端 usage | 等待时间 | 人工检查 |
|---|---:|---|---:|---:|---:|---|
| 库存超时 | 5 次，全部 504 | `SUCCEEDED` | 3 / 2 | 5877 token | 17.5s | 引用有效；归因措辞需修订 |
| 正常对照 | 5 次，超时率 0% | `SUCCEEDED` | 3 / 2 | 4973 token | 14.1s | 本窗口未发现库存超时，表述基本符合证据 |
| 无请求 | 0 次 | `INSUFFICIENT_EVIDENCE` | 3 / 1 | 1930 token | 6.7s | 应用证据门槛生成结果，模型只选择工具 |

表中的 token 是各条最终执行记录里服务端返回的完整 usage，不包含此前失败尝试可能产生的用量；等待时间包含客户端轮询。三条结果都通过状态和引用 ID 检查，这不等于语义准确率。

实际遇到的失败：首次库存超时任务在第二轮遇到 20 秒 `MODEL_TIMEOUT`，改为 45 秒后完成。无请求任务曾两次在第二轮返回 `INVALID_MODEL_OUTPUT`；现在应用在工具取回 `requestCount=0` 后直接返回证据不足，并记录 `EVIDENCE_GATE`，避免再发起最终模型请求。

库存超时的最终结论仍有两处越过证据边界：把 300ms 的请求总时限称为“读取超时”，还写了库存服务“不可用”，而当前样例证据只支持它响应变慢并触发请求超时。一次较早的输出也把相近的订单与库存 p95 说成“订单耗时完全由下游决定”。这些句子需要人工修订；窗口 p95 和引用存在本身不能证明因果关系。

所有请求都来自本地故障实验，没有生产流量。20 案例留出集和“仅检索文档”对照尚未运行，不能据此推断一般 Java 服务故障的诊断能力。
