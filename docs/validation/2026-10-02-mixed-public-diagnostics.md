## REST 同一窗口内的结果

工作流先按原 V3 模式验证下游、Callable、显式包装的 DeferredResult、并发和迟到调用，再启动另一组隔离进程，使用 V4 请求分类。八个接口在同一窗口里各自排查，所有记录随后从历史回读：

| 场景 | V4 分类 | 结果 |
|---|---|---|
| 原有主人详情：两次 200 和一次 404 | 执行异常为零，响应 2xx/4xx 分开 | 证据不足，不推断具体 404 根因 |
| 辅助同步异常 | 一个执行异常，有对应事件和规则 | 确认请求执行异常阶段 |
| 直接返回 503 | 一个仅 5xx 响应，执行异常为零 | 证据不足 |
| 捕获真实 HTTP 调用超时后返回 504 | V4 只采集一个仅 5xx 响应 | 证据不足，不把未采集下游倒填成已测超时 |
| Callable 内抛出异常 | 一个执行异常 | 确认请求执行异常阶段 |
| Servlet DeferredResult 超时 | 一个异步超时，执行异常为零 | 证据不足，不替代执行异常 |
| 返回 204 后下游调用迟到 | 成功响应，无执行异常 | 证据不足，已完成请求不接纳迟到结果 |
| 同一接口先异常，随后返回 204 | 两个请求：一个执行异常、一个成功响应 | 窗口仍报告曾观察到异常；成功响应不抹去过去异常 |

V3 的对应下游及异步超时场景继续支持原有下游超时判断。V4 刻意不观察下游，所以对同类业务调用只能报告已采集的 HTTP 响应。辅助接口构造的故障不表示原项目自身存在该问题。

## SQL 与 HTTP 对照

Petclinic 在原有 JPA 验收上增加一项检查：辅助接口实际执行错误 SQL，应用捕获异常后返回 503。同一次业务操作在数据库 V2 中有 SQL_QUERY_FAILED 和对应计数、规则，支持 SQL 执行阶段失败；在 HTTP V4 中只有仅 5xx 响应，执行异常计数为零，仍返回证据不足。连接获取超时、释放后的正常查询和旧模式继续通过。

## 保留的失败与范围

[首次对照失败](https://github.com/MoChiUaena/agent-triage/actions/runs/36991381314)发生在辅助场景尚未加入时：不存在的路径经上游错误处理返回 500，与预期的直接 503 冲突，证明新增断言能发现缺少场景。[第二次失败](https://github.com/MoChiUaena/agent-triage/actions/runs/36991728652)来自脚本查错文案位置：限制内部根因的措辞已在阶段判断正文中，断言却只检查不确定性栏。修正脚本后全部通过，没有为此改变生产判断。

验收使用 Linux、JDK 21、H2、固定规则模式和本地延迟 HTTP 服务，没有付费模型调用。原始 JSON、日志、数据库、密钥和公开项目副本留在忽略目录。已有 v0.10.0 标签和附件保持不变；更多驱动、远程拓扑、任意客户端、模型供应商的持续混合故障和数天运行仍需分别验证。
