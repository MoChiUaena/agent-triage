# 接入现有 Java 应用

当前适合接入本机单实例、JDK 21 的 Spring MVC 应用。先选择需要的观测能力，再修改依赖、配置和构建流程。登记源码不会自动产生运行指标，也不需要为了试用先配置付费模型。

[Spring Petclinic](PETCLINIC.md)验证了 Spring Boot 3.5.0、MVC 页面与 JPA；[Petclinic REST](validation/2026-09-30-petclinic-rest.md)验证了 Spring Boot 3.4.0、上下文路径与 REST 接口。两个项目都固定上游提交，最近复验见[接入核对记录](validation/2026-10-02-application-adoption.md)。这不是所有 Spring Boot 版本、数据库驱动或业务负载的兼容认证。SDK 按 Java 21 编译，JDK 17 不能直接加载；Boot 2.x 不在当前 Jakarta Servlet 接入范围内，Boot 4、WebFlux 和多实例目前没有接入验收。

## 按能力增加改动

| 需要的能力 | 应用侧改动 | Agent 侧改动 |
|---|---|---|
| HTTP 请求窗口 | 添加 Starter，配置服务身份、请求前缀和观测窗口 | 登记本机地址、身份与 V1 协议 |
| 下游 HTTP 超时 | 配置被观测 origin，使用 Spring 注入的 `RestClient.Builder` 创建客户端 | 登记对应下游身份 |
| 按 MVC 接口排查 | 开启 `endpoint-observations`；可选响应分类 | 改为 V3 协议，产生请求后选择接口 |
| 业务异常位置 | 开启异常位置，明确业务包范围 | 绑定同一服务的本机源码索引 |
| 核对源码版本 | 构建时生成源码与 class 摘要清单，重新打包 | 登记与运行构建对应的源码，变更后重新索引 |
| 跨类异常摘要 | 在应用 JVM 启动时另加可选 Java Agent | 沿用本机源码核对，不获得完整调用轨迹 |
| JPA/JDBC 阶段 | 开启 JPA 观测，显式包装原有 Hikari `DataSource` | 同地址另登记数据库服务与 V2 别名 |
| MVC Callable/WebAsyncTask | 显式开启自动上下文传播 | 沿用接口窗口 |
| 自建线程、DeferredResult 等 | 在提交任务的位置捕获快照并包装任务 | 不改变服务地址或窗口契约 |
| 模型辅助排查 | 应用仍提供相同观测；敏感内容先在接入方移除 | 在模型页配置服务，源码读取另行授权 |

HTTP Starter 目前仍要求下游身份和地址。没有 HTTP 下游的 Petclinic 使用 `unobserved-http` 与 `http://127.0.0.1:1` 作为占位，不向它生成请求；这项配置负担尚未消除。只观察某一 origin，不等于覆盖应用内的所有 HTTP 客户端：自行创建的 `RestClient`、RestTemplate、WebClient、Feign 和任意 JDK HttpClient 调用尚未验证自动归属。

Starter 尚未发布到 Maven Central，需要安装发布附件或自行构建后安装到 Maven 本地仓库。SDK 本身依赖 Spring Web 和 HikariCP，不把 Agent 的模型、历史库和源码索引放入业务应用。Maven 构建摘要示例见 [Starter](STARTER.md)；Gradle、多模块聚合及代码生成目录仍需另行评估。

## 两个公开项目实际增加了什么

两个准备脚本都向 POM 增加一项 Starter 依赖和一项摘要构建插件，并新增一个验收辅助配置类，原有业务文件保持原样。修改 POM 后必须重新构建、启动应用；服务白名单变更也需要重启 Agent。源码登记或重新索引可以在页面完成。

辅助配置类包含故障入口和专用参数，不是业务接入的必需部分。REST 的辅助类默认关闭，只在验收时开启，提供超时、业务异常和异步对照。Petclinic 的 JPA 配置把池设为一个连接、300 ms 获取时限以复现池耗尽；实际应用不要照搬这些故障参数。

JPA 包装必须保留原有连接池配置与生命周期。`DataSourceProperties` 初始化示例只说明包装入口，不会自动代替原来对 `spring.datasource.hikari.*` 的绑定。已有 `DataSource` Bean 时，应沿用它的 URL、凭据、池大小、获取时限和其他设置，再接入包装。当前只验证单个 Hikari 池，最大连接数为 1..64；多个数据源、动态路由池、XA 和更大的池不能直接套用这一验收。关闭观测器停止采样，关闭应用拥有的连接池仍由应用负责。

原有页面和 REST 接口用于核对真实请求、响应和源码入口；辅助接口用于构造额外故障。前者证明原接口能够接入，后者不证明原项目存在该故障。公开项目验收跳过了上游完整测试套件；现有业务回归仍应由接入项目运行。

## 一次接入的检查顺序

1. 在可恢复的项目分支安装 Starter，选择请求前缀和能力，保留原有数据源、客户端及超时配置。
2. 重新构建应用，确认原来的正常请求与错误处理仍按原样工作。需要源码核对时，在同一次构建中生成摘要清单。
3. 在 Agent 的启动白名单登记真实服务身份和回环地址。应用有 `/petclinic` 等上下文路径时，将它包含在 `base-url` 中；请求前缀仍按应用内的路由填写。
4. 先产生少量业务请求，确认只读观测的身份、窗口与计数；再登记源码并运行页面的接入检查。
5. 分别核对正常、失败与恢复窗口。404、SQL 查询失败、连接获取超时和下游超时不应被互相替代。
6. 用固定规则模式确认引用、历史和停止行为，再按需开启模型。业务目录、数据库、密钥及原始日志留在本机。

本机观测令牌默认关闭。开启时，两边配置必须一致；令牌只限制观测接口读取，没有替 Agent 页面提供多用户登录。Docker、远程主机和多个应用实例不能直接用当前回环白名单代替网络接入设计。

## 运行成本与限制

- HTTP 记录来自请求完成阶段，异步响应和跨线程包装会增加请求上下文的生命周期；没完成的请求还不进入完成计数。
- 默认请求容量 10000、窗口 15 分钟，额外保留两分钟供冻结窗口读取。每秒 20 条记录仅覆盖 15 分钟就需要约 18000 条；JPA 一次 HTTP 请求可能产生多条 JDBC 记录。容量不足时返回 422，需要缩小窗口或调整容量，不能继续用剩余样本生成完整判断。
- 查询窗口需要复制、排序样本，记录和查询共享采集器锁。中高负载下的业务尾延迟、CPU 和原生内存还没有对照测量。
- Java Agent 的类查询曾在固定 Petclinic 的 200 次直接测量中得到约 1.3 ms 的 p95。应用内自动查询最多 20 次/秒，超出时摘要保持未知。[原始范围](validation/2026-09-30-runtime-class-lookup.md)不包含 HTTP 往返，也不能作为其他应用的延迟保证。
- [五分钟资源检查](validation/2026-10-01-runtime-resources.md)使用受控任务、内存 H2 和固定堆。其堆值不是整个 Spring Boot 应用的内存需求，没有证明数天运行或真实供应商取消的成本。
- 历史使用 H2/PostgreSQL 保存，源码项目按文件数、字节数和索引时限限制；可以登记一个模块目录。默认不自动删除历史，页面提供预览后清理终态记录；本地模型密钥和历史库需要一起备份。

下一阶段先提供明确的入站请求观测模式，让没有 HTTP 下游的应用无需占位配置，再增加有证据约束的请求执行阶段失败判断。4xx 根因、完整分布式链路、更多 HTTP 客户端和数据库内部根因仍分别评估。
